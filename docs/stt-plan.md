# 음성 질의 확장 기획서 (v2)

기간: 3일 (10/13 ~ 10/15) · v1 대비 변경점은 [부록 A](#부록-a-v1에서-바뀐-것)

---

## 1. 목적

한 줄 목표: **음성 질문이 들어와도 근거 없는 답변 0건을 유지하고,
어느 구간이 느려지거나 멈춰도 정해진 시간 안에 안전한 응답을 돌려준다.**

| 채울 공백 | 이 확장으로 생기는 근거 |
|---|---|
| STT (음성 → 텍스트) | 음성 질문을 받아 기존 파이프라인에 연결 |
| 지연·장애 대응 | 구간별 지연 측정, 데드라인, 대체 경로, 장애 주입 |
| 백엔드 API | FastAPI 음성 질의 엔드포인트 |

TTS는 만들지 않습니다 (다른 프로젝트에서 출시 경험 확보).

---

## 2. 범위

**포함** — 음성(wav) → STT → 기존 파이프라인 → 텍스트 응답, 구간별 지연 측정,
데드라인과 대체 경로, 워밍업, 장애 주입 테스트, FastAPI 엔드포인트 1개.

**제외**

| 항목 | 이유 |
|---|---|
| TTS | 범위 밖 |
| 실시간 스트리밍(WebSocket) | 3일 초과. 면접에서 "다음 단계"로 설명 |
| 전화망 연동 | 범위 초과 |
| 동시 접속·부하 테스트 | 단일 사용자 로컬 환경으로 명시 |
| **가드 임계값 재조정** | 0.56 / 0.50을 음성에 맞춰 바꾸지 않는다. 바꾸면 기존 평가가 무효가 된다 |
| **조항 번호 정규식 확장** | 아래 3-2 참고. 오탐을 새로 만든다 |

## 3. 설계 결정

### 3-1. STT는 로컬에서 실행한다

외부 STT API를 쓰면 "사내 문서와 질문이 외부로 나가지 않는다"는 핵심 제약이 깨집니다.
`faster-whisper`를 로컬 GPU에서 돌립니다.

### 3-2. 조항 번호 정규식은 넓히지 않는다

STT가 `"제27조"`를 `"27조"`로 받아쓸 수 있습니다. 현재 정규식은 `제\s*(\d+)\s*조` 라
`제`가 없으면 매칭되지 않습니다. 그렇다고 `제?\s*(\d+)\s*조` 로 넓히면 **오탐이 생깁니다.**

```
3조 2교대 근무는 어떻게 돼?   → 제3조(용어의 정의) 조회
2조 격일제로 일하면 수당은?    → 제2조(적용범위) 조회
1조당 인원이 몇 명이야?        → 제1조(목적) 조회
```

규정에 없는 질문이 거부되지 않고 **엉뚱한 조항을 정확 일치(1.0)로 반환**합니다.
가드를 우회하는 경로라 단순 오인식보다 나쁩니다. 그래서 정규식은 그대로 둡니다.

대신 `제` 누락 변형 2~3개를 **점수에 넣지 않고 관찰로만** 기록하고,
README 다음 단계에 "'제' 누락 처리 시 교대조 표현과의 충돌 검토 필요"로 남깁니다.

### 3-3. 한글 숫자 정규화는 STT 출력에만 적용한다

Whisper가 `"제 이십칠 조"` 처럼 한글 숫자로 받아쓰면 정규식이 실패합니다.
한글 숫자 → 아라비아 숫자 변환을 **STT 출력 직후에만** 넣습니다.
텍스트 입력 경로는 손대지 않으므로 기존 평가 결과가 그대로 유지됩니다.

정규화 **전/후 인식률을 둘 다 기록**해 "문제 발견 → 해결"을 숫자로 남깁니다.

### 3-4. 데드라인은 음성 경로 전용 함수에만 건다

`ollama.chat()`은 블로킹이라 중간에 끊을 수 없습니다. 스트리밍(`stream=True`)으로 받으면서
데드라인을 검사하고, 넘기면 **부분 답변을 버리고** 근거 조항 원문을 반환합니다.
중간에 잘린 답은 틀린 답이 될 수 있어, "불확실하면 지어내지 않는다"는 원칙과 맞춥니다.

기존 `answer_with_history()`는 **수정하지 않습니다.** 음성 경로 전용 함수를 새로 만듭니다.

> 스트리밍을 중단해도 Ollama 서버는 생성을 계속할 수 있습니다.
> 제너레이터를 닫아 연결을 끊고, `ollama ps` 로 실제로 멈췄는지 확인합니다.

스트리밍을 쓰면 **TTFT(첫 토큰까지 시간)** 도 측정할 수 있습니다.
음성에서는 이 값이 전체 시간보다 체감에 가깝습니다.

## 4. 구조

```
음성 파일(wav)
  → [STT]            faster-whisper, 로컬 GPU
  → [숫자 정규화]     한글 숫자 → 아라비아 숫자 (STT 출력에만)
  → [임베딩 + 검색]   bge-m3, NumPy 벡터 스토어          (기존)
  → [가드 판정]       judge_evidence()                   (기존, 변경 없음)
  → [LLM 생성]        Ollama qwen2.5:7b, 스트리밍 + 데드라인
  → 텍스트 응답
```

판정은 기존 `judge_evidence()` 를 그대로 공유합니다 — **판정은 공통, 채널만 개별**입니다
(Streamlit / CLI / MCP / HTTP).

## 5. 기능 명세

### F1. STT 입력
- 입력: wav (16kHz 모노)
- 출력: 인식 텍스트, 평균 log 확률, 무음 확률
- 정규화 후 텍스트가 기존 질문 입력과 똑같이 파이프라인에 들어감

### F2. 구간별 지연 측정

기존 JSONL 감사 로그에 필드를 추가합니다. **새 필드 기본값은 `None`** 이라
기존 텍스트 경로 호출이 깨지지 않습니다 (텍스트 입력이면 `stt_ms` 는 `null`).

| 필드 | 의미 |
|---|---|
| `audio_sec` | 입력 음성 길이 |
| `stt_ms` | STT 소요 시간 |
| `normalize_ms` | 숫자 정규화 소요 시간 |
| `retrieval_ms` | 임베딩 + 검색 |
| `guard_ms` | 가드 판정 |
| `ttft_ms` | 첫 토큰까지 시간 |
| `llm_ms` | LLM 생성 (거부 시 0) |
| `total_ms` | 전체 |
| `stt_text_raw` | 정규화 전 STT 원본 |
| `stt_text` | 정규화 후 |
| `fallback` | 대체 경로 종류, 아니면 `null` |

### F3. 지연 예산과 대체 경로

**Day 1 실측으로 재배분했습니다** (initial_prompt 사용, 첫 요청 콜드 제외, n=39).

| 구간 | v1 | v2 | **v3 (실측 반영)** | 실측 p50 / p95 | 초과·실패 시 |
|---|---:|---:|---:|---:|---|
| STT | 1.5초 | 1.5초 | **0.6초** | 0.239 / 0.344초 | 신뢰도 낮으면 재질문 |
| 임베딩 + 검색 | 0.3초 | 0.1초 | **0.1초** | 0.012 / 0.027초 | "확인 후 안내드리겠습니다" |
| 가드 판정 | 0.05초 | 포함 | 포함 | 0.000초 | 근거 없으면 LLM 호출 없이 거부 |
| LLM 생성 | 1.0초 | 1.3초 | **2.0초** | 0.287 / 1.025초 | 부분 답변 버리고 근거 원문 반환 |
| 여유 | 0.15초 | 0.1초 | **0.3초** | | |
| **합계** | 3.0초 | 3.0초 | **3.0초** | 전체 p95 **1.288초** | |

STT 실측 RTF 가 **0.086**(최대 0.133)으로 목표 0.3을 크게 밑돌아, 1.5초 배정은 과했습니다.
5초 음성이어도 0.43초면 끝납니다. 줄인 0.9초를 **LLM 쪽으로 넘겼습니다** — 실측 p95가
1.025초라 v2의 1.3초 예산이 빠듯했고, 답변이 길어지면 데드라인이 자주 걸릴 수 있습니다.

전체 p95가 1.288초로 예산 3.0초의 **43%** 수준이라, 데드라인은 평상시에 발동하지 않고
장애 상황에서만 동작합니다. 그게 의도한 설계입니다.

> **콜드 스타트는 별개입니다.** 첫 요청은 검색 2.584초(임베딩 모델 로드)로
> 전체 3.368초가 걸렸습니다. 워밍업(F4)이 겨냥하는 지점이 바로 여기입니다.
### F4. 워밍업
서버 시작 시 bge-m3, STT, qwen2.5를 미리 로드하고 더미 요청 1회.
Ollama `keep_alive`(30분)로 모델이 메모리에서 내려가지 않게 유지.

**비용을 없애는 게 아니라 서버 시작 시점으로 옮기는 것**이므로, 시작 시간 증가와
VRAM 점유를 함께 측정합니다. 결과는 부록 C.

### F5. 장애 주입 테스트

| 시나리오 | 방법 | 기대 결과 |
|---|---|---|
| LLM 서버 다운 | Ollama 중지 | 근거 조항 원문 반환 |
| LLM 지연 | 생성에 인위적 지연 | 근거 조항 원문 반환 |
| 검색 지연 | 검색 함수에 인위적 지연 | 확인 후 안내 응답 |
| 무음·잡음 입력 | 무음 wav | 재질문 응답 |

### F6. FastAPI 엔드포인트
`POST /ask-voice` — 음성 파일을 받아 응답 텍스트, 근거 조항, 판정, 구간별 지연을 반환합니다.
판정은 기존 `judge_evidence()` 를 공유합니다.

**단일 워커로 띄우므로 동시 요청은 순차 처리됩니다.** 모델이 GPU 를 점유해
워커를 늘리면 VRAM 이 배로 듭니다. 동시 접속·부하는 범위 밖입니다(2장).

## 6. 녹음 세트

**ffmpeg을 쓰지 않습니다.** 질문을 화면에 띄우고 Enter로 16kHz 모노 wav를 저장하는
녹음 스크립트를 만듭니다. 파일명을 질문 ID로 저장하므로 라벨이 섞이지 않고
마이크 조건도 일정하게 유지됩니다.

| 세트 | 개수 | 용도 | 비고 |
|---|---:|---|---|
| **평가셋** | 40 | 보고용 (텍스트 결과와 1:1 비교) | 기존 `QUESTIONS` 30 + `HOLDOUT` 10 |
| **번호 세트** | 15 | 조항 번호 인식률 | 제1~31조 고르게, **`제N조` 형태만** |
| **모델 선택용** | 10 | small/medium 비교 전용 | 평가셋과 겹치지 않음 |
| **관찰용** | 3 | 점수 제외 | `제` 누락 변형, 교대조 표현 |
| **합계** | **68** | | 약 1시간 |

### 6-1. 녹음 규칙 (측정 타당성)

번호 인식률이 **STT 성능이 아니라 읽는 방식의 차이**를 재게 되면 지표가 무의미해집니다.

- 화면에 `제27조`가 떠도 **실제 사용자처럼 자연스럽게 "제이십칠조"** 라고 읽습니다.
  `"제 이 칠 조"` 처럼 숫자를 하나씩 끊어 읽지 않습니다.
- 68개 내내 **같은 방식**으로 읽습니다. 중간에 바뀌면 그 차이가 결과에 섞입니다.
- **마이크와의 거리를 일정하게** 유지합니다.
- 한 번에 몰아서 녹음합니다 (목 상태·주변 소음 변화를 줄이기 위해).

### 6-2. 번호 세트의 숫자 선택

| 조 번호 | 의도 |
|---|---|
| 제2 · 제12 · 제22 | "이 / 십이 / 이십이" 혼동을 직접 확인 |
| 제20 | "이십"은 끝자리가 없어 `제2조`나 금액 `20조`로 흘릴 위험 |
| 제31 | 마지막 조항, 경계값 |

한 자리 5개 / 두 자리 10개로 맞췄습니다.

모델 선택을 평가셋 40문항으로 하면 **같은 데이터로 고르고 보고하는** 구조가 됩니다.
가드 임계값에 홀드아웃을 둔 것과 같은 이유로, 모델 선택용 10문항을 따로 둡니다.

## 7. 목표 지표

모든 목표는 **초기 가설**입니다. Day 1 베이스라인 후 조정할 수 있지만 이유를 기록합니다.
**결과를 맞추려고 목표나 임계값을 바꾸지 않습니다.**

| 구분 | 지표 | 목표 | 왜 이 지표인가 |
|---|---|---|---|
| **안전 (필수)** | 음성 입력 기준 근거 없는 답변 | **0건** | 깨지면 다른 지표가 무의미 |
| 정확도 | STT 문자 오류율 (CER) | **10% 이하** | 한국어는 단어보다 문자 단위가 정확 |
| 정확도 | 조항 번호 인식률 (15문항) | **14/15 이상** | 숫자 하나만 틀려도 엉뚱한 조항 |
| 정확도 | 숫자 정규화 전/후 인식률 | 둘 다 기록 | 문제 발견 → 해결을 숫자로 |
| 일관성 | 텍스트와 같은 판정 비율 | **38/40 이상** | STT 오인식이 가드를 얼마나 흔드는지 |
| 일관성 | 오거부 증가 | **2건 이하** | 텍스트 기준 0건 대비 |
| 일관성 | 근거 조항 적중 (규정 안 18) | **17/18 이상** | 텍스트 기준 18/18 대비 |
| 지연 | STT RTF (처리/음성 길이) | **0.3 이하** | 5초 음성을 1.5초 안에 |
| 지연 | 전체 p50 / p95 (워밍업 후) | **2.0 / 3.0초 이하** | 지연 예산 3.0초 |
| 지연 | TTFT p50 | 기록 | 음성에서는 체감에 더 가까움 |
| 지연 | 거부 경로 전체 시간 | **STT + 0.05초 이내** | 거부는 LLM 호출 0회 |
| 지연 | **첫 요청 응답 시간** | **베이스라인 재측정 후 설정** | 아래 7-1 |
| 장애 | 장애 주입 4개 대체 응답 | **4/4** | 설계가 실제로 동작 |
| 장애 | 대체 응답까지 시간 | **구간 예산 + 0.2초 이내** | 장애가 나도 끊기지 않음 |

### 7-1. 콜드 스타트 베이스라인은 다시 잰다

v1은 "2.2초 → 0.8초"로 적었지만, **2.2초는 콜드 상태에서 18건 생성의 평균**이지
첫 요청 하나의 응답 시간이 아닙니다. 실제 첫 요청은 **7.2초**가 걸린 관측이 있습니다.

Day 2에 "서버 시작 후 첫 요청"을 명확한 절차로 재측정합니다
(Ollama 재시작 + 새 파이썬 프로세스 → 첫 요청 1회). **2.2초는 사용하지 않습니다.**

### 8-1. Windows CUDA DLL 처리 (재현에 필요)

`ctranslate2` 가 `cublas64_12.dll` 을 못 찾아 CUDA 초기화에 실패합니다.

### 안전: 가드 통과 1건, 최종 응답 0건

`반려동물 동반출근 가능해?`(규정 밖)에서 **1차 방어선인 가드가 뚫렸습니다.**

| | 1순위 | 2순위 | 보조 근거 | 가드 |
|---|---:|---:|---:|---|
| 텍스트 `동반출근` | 0.4966 | **0.4920** | 0개 | 거부 ✅ |
| 음성 `동반 출근` | 0.5100 | **0.5088** | **2개** | 통과 ❌ |

STT 가 만든 **띄어쓰기 하나**가 두 점수를 0.50 위로 밀어올려 보조 근거 규칙이 발동했습니다.
`docs/evaluation.md` 에 **"보조 근거 기준 0.50 의 여유가 +0.008 로 얇다"** 고 적어둔
그 0.4920 이 바로 이 질문입니다. **한계로 기록해둔 지점이 음성 노이즈에서 실현됐습니다.**

**다만 사용자에게 나간 답은 거부였습니다.** 가드를 통과한 뒤 LLM 이 스스로 막았습니다.
생성 단계의 실제 응답은 다음 한 문장이었고, 3회 반복 모두 같았습니다.

```
규정에 없습니다.
```

| 지표 | 값 | 의미 |
|---|---:|---|
| 가드 통과 (규정 밖) | **1건** | 1차 방어선이 뚫린 횟수 |
| 근거 없는 답변 (최종) | **0건** | 사용자에게 나간 답 |

두 지표를 분리해야 하는 이유는, 둘 다 사용자에게는 거부로 보이지만 **안전장치가
어디서 작동했는지가 다르기 때문**입니다. 가드가 막으면 LLM 호출이 0회지만,
LLM 이 막으면 호출 비용이 들고 모델이 바뀌면 결과도 바뀔 수 있습니다.

임계값은 **바꾸지 않습니다.** 음성 결과에 맞춰 0.50 을 올리면 텍스트 평가 40문항이
무효가 되고, 이번엔 운 좋게 맞춘 숫자가 됩니다 (2장 제외 항목).

**다음 단계는 BM25 하이브리드입니다.** 띄어쓰기 변화로 벡터 점수가 0.017 움직이는 것이
원인인데, 키워드 매칭은 `동반출근`/`동반 출근` 을 같은 토큰으로 보므로 이 흔들림에 강합니다.
임계값을 건드리지 않고 입력 노이즈 내성을 올리는 방향입니다.

**판정 일치의 주 지표는 사전 정의대로 '가드 판정' 기준 38/40 입니다.**
차이 1건은 eval19 로, **가드는 통과했고 LLM 이 `규정에 없습니다` 로 거부**한 건입니다.
최종 응답 기준으로 세면 39/40 이 되지만, 그렇게 바꾸면 "가드가 뚫려도 LLM 이 막으면
일치"가 되어 지표가 느슨해집니다. **원래 정의로도 목표(≥38/40)를 충족하므로
정의를 바꿀 이유가 없습니다.** 39/40 은 보조로만 함께 보고합니다.

> (`제3조`, `제27조`)는 STT 가 원래 정확히 받아써 정규화가 발동하지 않았습니다.

### 가설과 실측의 차이 — 번호 인식

v2 는 `제27조` 가 **한글 숫자**(`제이십칠조`)로 받아써질 것을 걱정했습니다.
설계 세트 15문항에서는 **한 번도 나오지 않았고**, 다른 오류가 나왔습니다.

| 가설 (v2) | 설계 세트 실측 | 신규 세트 실측 |
|---|---|---|
| 숫자가 한글로 → `제이십칠조` | 발동 0건 | **1건 발동** → `제육조` |
| — | **단위 글자** → `제11주는`, `제 20초` | 없음 |
| — | **'제' 소실** → `채용 5조가` | 없음 |

**설계 세트만 봤다면 "한글 숫자 가설은 틀렸다"로 끝났을 것입니다.** 신규 5문항에서
`제6조` 가 `제육조` 로 나와 `normalize_article_numbers()` 가 실제로 작동했습니다.
한 자리 숫자에서만 나타났는데, n 이 작아 원인을 단정할 수는 없습니다.
**발동 0건이라고 지우지 않은 판단이 맞았습니다.**

실측에서 나온 단위 글자 오류를 겨냥해 `normalize_unit_slip()` 을 추가했습니다.

```
제11주는   →  제11조는      조사(는/가/를...)가 바로 붙을 때만 바꾼다
제3주차     →  제3주차        '차'가 오면 진짜 '주(week)' 이므로 그대로
제2주 교육  →  제2주 교육     공백이 오면 구분할 수 없으므로 그대로
```

오탐 탐침 6개(`제3주차 교육`, `제2주 교육 일정`, `20초 동안`, `3주 동안 휴가`,
`제2주간 근무표`, `제1주년 행사`)를 먼저 통과시키고 넣었습니다. **21/21 통과.**

### F4 워밍업 — 비용을 없앤 게 아니라 옮긴 것

첫 요청이 느린 이유는 임베딩 모델(bge-m3) 로드가 **요청 경로 안에서** 일어나기
때문입니다. 워밍업은 이 비용을 **서버 시작 시점으로 옮깁니다.** 없애는 게 아니므로
서버 시작이 얼마나 느려지는지도 함께 재야 트레이드오프가 보입니다.

측정 절차: `ollama stop qwen2.5:7b` → 새 파이썬 프로세스 → 첫 요청 1회

| | 워밍업 없음 | 워밍업 | 차이 |
|---|---:|---:|---:|
| 서버 시작 | 7.98초 | 13.30초 | **+5.32초** |
| **첫 요청** | **5.18초** | **0.79초** | **−4.39초** |

워밍업 내역: 임베딩+색인 9.46초 / LLM 2.80초 / STT 0.32초
첫 요청 내역(워밍업 후): STT 230ms / 검색 11ms / LLM 549ms

**VRAM 점유**

| 시점 | 사용량 |
|---|---:|
| 기동 전 | ~2.9GB |
| 워밍업 없이 시작 직후 | 3.68GB |
| **워밍업 후 시작 직후** | **11.05GB** |

`keep_alive=30m` 으로 Ollama 가 모델을 메모리에 붙잡아 둡니다. 12GB 카드에서
**11GB 를 상시 점유**하므로, 같은 GPU 로 다른 작업을 돌릴 여유가 거의 없습니다.
단일 사용자 로컬 환경이라 받아들인 선택이고, 공유 GPU 라면 `keep_alive` 를 줄이고
첫 요청 지연을 감수하는 쪽이 맞습니다.

> **v1 의 "콜드 스타트 2.2초" 는 폐기했습니다.** 그 값은 콜드 상태에서 18건 생성의
> 평균이었지 첫 요청 시간이 아니었습니다. 같은 절차로 다시 재니 **5.18초** 입니다.
> 이력서에는 **5.18초 → 0.79초 (서버 시작 +5.3초)** 로 씁니다.

### F6 FastAPI — 네 번째 표면

`POST /ask-voice` 로 wav 를 받아 응답·근거·판정·구간별 지연을 돌려줍니다.
판정은 기존 `judge_evidence()` 를 그대로 공유합니다 — **판정은 공통, 채널만 개별**
(Streamlit / CLI / MCP / HTTP).

실제 호출 결과:

| 질문 | `passed_by` | 답변 | 전체 |
|---|---|---|---:|
| 연차 며칠 쓸 수 있어? | `strong` | 15일의 유급휴가 (제12조) | 1181ms |
| 제27조가 뭐야? | `exact` | 제27조는 징계 사유를 정한 조항 | 1495ms |
| 반려동물 동반 출근? | `support` | **규정에 없습니다** | 467ms |

세 번째가 Day 1 에서 가드가 뚫린 그 질문입니다. API 응답에도 `has_evidence=true`,
`passed_by="support"` 가 그대로 드러나, **1차 방어선이 통과시켰고 생성 단계가 막았다**는
사실이 호출자에게 보입니다.

**한계: 단일 워커입니다.** `uvicorn ... workers=1` 로 띄우므로 **동시 요청은 순차
처리됩니다.** 모델이 GPU 를 점유하는 구조라 워커를 늘리면 VRAM 이 배로 듭니다
(위 표에서 1개 워커가 이미 11GB). 동시 접속·부하는 이번 범위가 아닙니다(2장).
